# Go research workspace (experimental)

This is a local diagnostic slice, not a replacement for the Python research, collectors, risk, execution, training or paper-live workflows. The existing Python inventory remains incomplete and is not authority to remove code. No production data or real orders are required.

Build the existing options UI with `npm ci --prefix options-ui && npm run build --prefix options-ui`. Start the Go server with `go run ./cmd/zenquant serve --engineering --research-store /path/to/isolated/store`, and open the printed `/research` URL. The research UI is embedded in Go; the existing options UI still requires its built assets. Use a dedicated store directory. CLI operations share the same store and JSON API: `zenquant workbench --store DIR import|list|snapshot|run|result|compare < request.json`. For example, list with `{"kind":"snapshot"}`, run with `{"snapshot_id":"<id>","fee_rate":0.001}`, and compare with `{"a":"<result-id>","b":"<result-id>"}`.

Import accepts JSON up to 1 MiB with `version: "dataset-v1"`, provider, venue, instrument `BTC`, timeframe (`5m`, `1h`, `4h`, or `1d`), `candles` and `funding`. Each candle has `symbol`, `timeframe`, `open_time_ns`, `close_time_ns`, `open`, `high`, `low`, `close`, `volume`, and `trade_count`; funding rows have `time_ns` and `rate`. Timestamps are integer Unix nanoseconds and are parsed in Go. Upload the original file without browser JSON editing to avoid JavaScript integer precision loss. Candle ordering, intervals, duplicates, values and funding ordering are checked. Gaps are recorded and block replay. Missing funding observations and unknown coverage are explicitly disclosed; observations do not establish historical availability.

Snapshot IDs hash the stored manifest, including the original source hash. The fixed diagnostic buys one BTC at the first candle close and sells at the last, with synthetic full fills at the same close, no slippage and only the latest visible funding row per bar. This is not live parity, a realistic execution model or evidence of profit. Results include episode accounting and are content-addressed; comparison requires the same snapshot and engine, and displays both fee rates. Files are synced and atomically linked without replacement, with hashes checked on reopen. Interrupted writes can leave unreferenced `.publish-` files; they are not automatically deleted.

The current synchronous implementation permits one active run per server instance and rejects an additional run. It has no durable job queue, progress display, UI cancellation, multi-process worker coordination, SQLite catalog, CSV/Parquet import, collector, complete cash/NAV and drawdown metrics, or desktop host. Its cancellation API applies within the Go process only. It is not the completed workbench plan. Keep this directory separate from production and paper state.
