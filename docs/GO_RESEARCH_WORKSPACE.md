# Go research workspace (experimental)

This is a local diagnostic slice, not a replacement for the Python research, collectors, risk, execution, training or paper-live workflows. The existing Python inventory remains incomplete and is not authority to remove code. No production data or real orders are required.

Build the existing options UI with `npm ci --prefix options-ui && npm run build --prefix options-ui`. Start the Go server with `go run ./cmd/zenquant serve --engineering --research-store /path/to/isolated/store`, and open the printed `/research` URL. The research UI is embedded in Go; the existing options UI still requires its built assets. Use a dedicated store directory. CLI operations share the same store and JSON API: `zenquant workbench --store DIR import|list|snapshot|submit|jobs|cancel|result|compare < request.json`. For example, list with `{"kind":"snapshot"}`, run with `{"snapshot_id":"<id>","fee_rate":0.001}`, and compare with `{"a":"<result-id>","b":"<result-id>"}`.

Nanosecond fields in workbench API responses are decimal strings; dataset import remains raw JSON with integer timestamps. Diagnostic v3 job and result identities bind the embedded Go research/workbench sources, Go version and binary64 contract. Queued jobs from another identity require explicit resubmission; historical result files remain unchanged. Results appear in the workspace only when linked to a succeeded job. Unlinked v1/v2 artifacts, including potentially legitimate pre-job results, require manual review of their preserved files; their origin cannot be established from an engine label. Legacy comparisons are rejected because the implementation identity is unverified. Cancellation is accepted only before the durable `committing` transition; after that cutoff publication is recovered to success or interruption.

Import accepts JSON up to 1 MiB with `version: "dataset-v1"`, provider, venue, instrument `BTC`, timeframe (`5m`, `1h`, `4h`, or `1d`), `candles` and `funding`. Each candle has `symbol`, `timeframe`, `open_time_ns`, `close_time_ns`, `open`, `high`, `low`, `close`, `volume`, and `trade_count`; funding rows have `time_ns` and `rate`. Timestamps are integer Unix nanoseconds and are parsed in Go. Upload the original file without browser JSON editing to avoid JavaScript integer precision loss. Candle ordering, intervals, duplicates, values and funding ordering are checked. Gaps are recorded and block replay. Missing funding observations and unknown coverage are explicitly disclosed; observations do not establish historical availability.

Snapshot IDs hash the stored manifest, including the original source hash. The fixed diagnostic buys one BTC at the first candle close and sells at the last, with synthetic full fills at the same close, no slippage and only the latest visible funding row per bar. This is not live parity, a realistic execution model or evidence of profit. Results include episode accounting and are content-addressed; comparison requires the same snapshot and engine, and displays both fee rates. Files are synced and atomically linked without replacement, with hashes checked on reopen. Interrupted writes can leave unreferenced `.publish-` files; they are not automatically deleted.

The server owns one cross-process worker lock and keeps a bounded queue of eight queued, running or committing jobs, with a maximum of 1,024 retained job records. If a submission reports durability unconfirmed, inspect the job ID in the error and job list before retrying; the record may already exist. The store fails closed on corrupt job metadata. Submitted jobs persist as queued, running, succeeded, failed, cancelled or interrupted. On restart a previously running job becomes interrupted and requires a new submission; queued jobs remain queued. A cancellation request for a running job is cooperative. Results are published before a success record. A crash can leave an unreferenced result or temporary file; neither is automatically deleted. Use a local filesystem with working advisory locks, atomic rename/link and fsync, and do not replace the store directory while in use. The server must be running to process CLI-submitted jobs. The job list is retained indefinitely and has no cleanup policy.

Results include a separate cash/NAV ledger starting at USD 100,000, close-to-close maximum drawdown, gross turnover, maximum close exposure, fees, funding and a reconciliation against episode net P&L. These are diagnostic calculations under the documented synthetic assumptions, not venue accounting. Older results do not contain these metrics and cannot be compared with the newer engine. The current implementation has no SQLite catalog, CSV/Parquet import, collector, or desktop host. It is not the completed workbench plan. Keep this directory separate from production and paper state.
